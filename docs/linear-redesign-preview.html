Information Architecture

菜单重组方案

组织原则:纵向按业务模式 —— 产品管理是上游(创建三类业务的产品),往下是 订阅运营 / 按量运营 / CodingPlan 三种业务模式,各业务的「账号」是该业务模式下的用户,跟随业务; 横向按跨业务职能 —— 用户运营(全局注册用户)、风控、营销、供给、财务、监控、系统。 重点修掉「监控审计」大杂烩与风控拆散两处;43 项不增不减,路由 path 全部不变,无需改路由与权限配置。

移动(紫底 = 移入新位置) 移出(删除线 + 去向) 业务模式纵向业务线 新组新建分组 瘦身8 项 → 3 项
现状11 组 · 43 项
提案固定区 + 11 组 · 43 项

调整理由

每一条移动都对应一个业务归位逻辑
1
三种业务模式纵向成体系
订阅套餐、按量、CodingPlan 是三种独立业务模式;产品管理是它们的上游 —— 三类业务的产品都在这里创建。菜单按 产品管理 → 订阅运营 → 按量运营 → CodingPlan 顺序排列,上游在前,三条业务线并列。
2
账号跟着业务走
订阅账号、按量账号是各业务模式下的开通实例(该业务的用户),保留在各自业务组内,统一放组内末位(配置在前、账号在后)。与全局「用户管理」严格区分。
3
用户运营只管全局身份
用户管理(所有注册用户)、用户分群、工单中心是跨业务的用户视角。「用户身份」更名「用户管理」,消除与认证体系的歧义;仅改文案,路由不动。
4
「监控审计」大杂烩拆解(8 → 3)
原 8 项混了可观测性、数据同步、增长分析、风控、合规、用户触达六类业务。拆完只留实时监控 / 告警中心 / Agent 观测,更名「监控告警」。
5
风控合并成组
风险用户(原在用户运营)与风控规则(原在监控审计)是同一业务的名单与规则两面,日常排查成对使用,合并为独立「风控」组。
6
公告是触达不是监控
公告是面向用户的触达内容,与活动、促销码同属运营触达手段,移入「营销」,更名「公告通知」。
7
业务漏斗上移到顶部
漏斗与运营总览同属决策视图,是高频入口,从监控审计移到顶部固定区,与总览并列。
8
Publisher 同步归供给侧
它是上游内容同步任务管理,与模型库、渠道管理同属供给链路运维,归入「供给与渠道」(原「模型与渠道」扩名)。
9
审计日志归系统
审计日志记录的是后台操作合规,与角色权限、后台账号天然一体,归入「系统」。

遗留路由说明

不在菜单中、但仍可深链访问的页面(维持现状,不在本次范围)
  • /api-keys · /usage · /revenue · /sessions · /model-access — 旧版页面,菜单不露出。其中 /usage(用量流水)对财务对账有价值,建议后续评估是否在「财务」组恢复入口。
Design Tokens

样式改造方案

保留 stsoft 纸色体系(米纸背景、暖调边框、墨色文字、柔和状态色全部不动), 结构与密度 Linear 化:靠 1px 边框分层而非大投影、小圆角、紧凑行高。 accent 从「深海蓝 #0E2A47 + 蜂蜜金 #E8B464」收敛为 克莱因蓝 #002FA7 单色, hover / 选中态也统一用克莱因蓝低透明度。浅色单主题,不引入深色模式。

提案 · 透明侧栏 + inset 圆角面板(header 在面板内)
  • 顶栏全宽 Header 68px + 面包屑→取消,改为面板内 40px view header
  • 内容区渐变米色背景直铺→8px 留边 + 1px 边框 + 8px 圆角的整体面板
  • 侧边栏240px 米色实底 + 右边框→244px 与背景同色,无边框,靠面板分层
  • 侧栏新增顶部搜索框(⌘K)+ 底部当前账号区,替代右上角用户下拉
  • 分组折叠不可折叠→组标题可折叠,状态记忆到 localStorage
